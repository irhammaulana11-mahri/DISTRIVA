# 33 — T4.2.1.1 ScopedAuthorizationService

**Dokumentasi:** v3.5.0  
**Tanggal:** 5 November 2026  
**Status:** Implementasi fondasi dan unit tests PASS; PostgreSQL service integration dan Policy NOT RUN.

## 1. Tujuan dan keputusan

Fondasi authorization menghubungkan assignment operasional dengan katalog permission tanpa membuat sumber assignment kedua:

- `user_role_assignments` adalah satu-satunya sumber role, unit, status, dan periode assignment pengguna.
- Spatie mengelola katalog `roles`, `permissions`, dan `role_has_permissions`; service tidak memakai user-role pivot, `HasRoles`, atau default `can()` resolver.
- Guard otorisasi mengikuti konfigurasi canonical `web`.
- Permission key diberikan oleh pemanggil; dokumen ini tidak menetapkan katalog permission baru atau membuat seeder.
- Default scope adalah unit yang sama. Akses UP3 ke ULP anak hanya memakai mode eksplisit `UP3_DESCENDANT_READ`; Policies mendatang hanya boleh menggunakan mode ini untuk operasi baca, bukan mutasi atau approval.
- Assignment global `SYS_ADMIN` hanya dapat mengevaluasi permission dalam konteks `SYSTEM` tanpa unit target. Role tersebut tidak mendapat akses bisnis atau approval secara implisit.
- Vendor harus lulus verifikasi assignment unit dan relasi vendor company + project + work order. Karena relasi domain belum tersedia, implementasi saat ini fail-closed.
- Service tidak menggunakan cache authorization pada tahap ini.

### API service

- `effectiveAssignments(User $user, ?CarbonImmutable $asOf = null): Collection` mengambil assignment pengguna yang aktif, berlaku pada tanggal bisnis, memakai guard canonical, dan memiliki unit aktif bila role mewajibkan unit.
- `allows(User $user, string $permission, AuthorizationContext $context, ?CarbonImmutable $asOf = null): bool` mengevaluasi status user/assignment, grant katalog, dan target scope. Denial normal menghasilkan `false`; exception query/konfigurasi tidak ditelan.

Tanggal awal/akhir assignment bersifat inklusif. Tanggal default ditentukan dalam timezone bisnis `Asia/Jakarta`. Model user, assignment, role, dan unit harus merupakan model persisted; assignment juga harus cocok dengan user yang sedang diperiksa.

## 3. Alur keputusan

1. Tolak user yang bukan `ACTIVE`, belum persisted, atau permission kosong.
2. Pastikan konteks scope valid: target unit untuk scope organisasi atau tanpa unit untuk `SYSTEM`.
3. Ambil assignment dari `user_role_assignments` untuk user tersebut; filter `is_active`, `valid_from`, `valid_until`, role/permission guard, dan unit aktif.
4. Pastikan permission yang tepat terhubung ke role melalui relasi Spatie `role_has_permissions`.
5. Untuk `SAME_UNIT`, cocokkan unit assignment dengan unit resource secara persis.
6. Untuk `UP3_DESCENDANT_READ`, terima UP3 assignment terhadap ULP anak langsung yang aktif; mode ini harus digunakan hanya oleh Policy read-only.
7. Untuk `SYSTEM`, hanya `SYS_ADMIN` global (`organizational_unit_id=NULL`) yang dapat lolos pemeriksaan role/unit; permission tetap wajib tersedia di katalog.
8. Untuk role `VENDOR`, wajibkan ketiga identifier scope dan panggil `VendorScopeAuthorizer`. Binding sekarang menolak semua karena belum ada relasi persisted yang dapat memverifikasi ketiganya.
9. Jika tidak ada assignment yang memenuhi seluruh syarat, tolak.

Service ini belum menerapkan filtering query list. Saat Policies/query services dibuat, scope record wajib diterapkan sebelum pagination.

## 5. Batasan dan risiko

- Unit tests menggunakan assignment/model in-memory agar tidak membuka koneksi database.
- Query Eloquent `effectiveAssignments()` belum diuji pada PostgreSQL setelah perubahan v3.5.0. SQLite bukan pengganti test PostgreSQL untuk constraint, trigger, exclusion, atau integrasi schema.
- Belum ada Policy, middleware, controller, atau route yang memanggil service; service belum menjadi enforcement aktif pada endpoint.
- Permission keys/mapping role-permission masih pending T4.4.
- Belum ada resolver vendor konkret; semua akses vendor saat ini ditolak.
- Belum ada assignment/unit write paths, atomic audit logging, cache invalidation, concurrency stress, atau Sanctum UUID end-to-end.
- Service tidak menjamin keputusan authorization dan mutasi bisnis atomik; write path nantinya harus melakukan pemeriksaan dan perubahan dalam batas transaksi yang tepat.
- Perubahan v3.5.0 tidak membuat atau menjalankan migration dan tidak terhubung ke database.
