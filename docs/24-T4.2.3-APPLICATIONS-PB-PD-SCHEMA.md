# 24 — T4.2.3 Database Schema: Permohonan PB/PD

**Versi dokumentasi:** 3.0  
**Status:** Rancangan database konseptual dan keputusan bisnis terkonfirmasi sebagian; belum menjadi migration Laravel.

## 1. Tujuan dan prinsip

Domain ini mengelola pelanggan, permohonan PB/PD, impor Bot Daftung, survei, referensi eksternal, pembayaran, status internal, task, dan SLA.

- `applications` adalah agregat utama proses PB/PD di DISTRIVA.
- Data sumber Bot Daftung disimpan dalam staging dan payload asli dipertahankan untuk audit/reprocessing.
- IDPEL adalah identitas pelanggan PLN; satu IDPEL dapat terkait dengan banyak permohonan. No. Register dan No. Agenda adalah referensi transaksi/proses pada masing-masing permohonan, bukan identitas pelanggan atau nomor aplikasi internal.
- IDPEL, No. Register, dan No. Agenda tidak wajib tersedia pada saat permohonan pertama kali dibuat; masing-masing diterima ketika diterbitkan oleh sistem PLN terkait.
- Status EIS AP2T/Bot Daftung tidak dicampur dengan status workflow internal.
- Informasi pembayaran yang diimpor tidak dianggap terverifikasi hanya karena ada nominal/tanggal pada spreadsheet.
- Nomor telepon wajib tersedia sebelum permohonan diajukan/diproses sebagai permohonan resmi; data staging boleh belum memiliki nomor telepon.
- Dokumen dan foto disimpan melalui modul dokumen/private storage, bukan sebagai blob di tabel domain.

## 2. Tabel pelanggan

### 2.1 `customers`

Kolom rancangan:

| Kolom | Tipe | Aturan |
|---|---|---|
| id | UUID | PK |
| customer_number | VARCHAR(50) | Unique, nomor internal DISTRIVA |
| name | VARCHAR(200) | Wajib |
| phone | VARCHAR(30) | Wajib sebelum submit; boleh NULL saat staging/pelengkapan |
| email | VARCHAR(150) | Nullable |
| created_at, updated_at | TIMESTAMPTZ | Audit waktu |

Nomor telepon disimpan sebagai string, bukan angka, agar tanda `+` dan awalan negara tidak hilang. Normalisasi E.164 direkomendasikan. Validasi nomor dilakukan sebelum submit. Nomor telepon yang belum tersedia masuk antrean pelengkapan oleh NIAGA_RETAIL; data impor tidak ditolak hanya karena field ini kosong.

Alamat layanan disimpan pada permohonan (`applications.service_address`) agar pelanggan dapat memiliki beberapa permohonan di lokasi berbeda. Alamat identitas pelanggan, jika kelak diperlukan, adalah atribut terpisah dan tidak otomatis menggantikan alamat layanan.

### 2.2 `customer_external_references`

| Kolom | Tipe | Aturan |
|---|---|---|
| id | UUID | PK |
| customer_id | UUID | FK customers |
| source_system | VARCHAR(50) | Contoh AP2T, BOT_DAFTUNG |
| reference_type | VARCHAR(50) | Contoh IDPEL |
| reference_value | VARCHAR(150) | Nilai sumber disimpan sebagai string |
| is_primary | BOOLEAN | Default false |
| valid_from, valid_until | TIMESTAMPTZ | Masa berlaku opsional |
| created_at, updated_at | TIMESTAMPTZ | Timestamp |

IDPEL bukan PK `customers`; calon pelanggan PB dapat belum memilikinya. Ketika IDPEL diterbitkan/ditemukan, referensi tersebut ditautkan ke customer internal yang sama. **Satu customer/IDPEL dapat memiliki banyak `applications`** (misalnya PB, PD, atau layanan lain pada waktu berbeda). Karena itu, IDPEL tidak disimpan pada tabel `applications` sebagai kolom identitas utama dan tidak boleh dibuat ulang untuk setiap permohonan.

Constraint yang direkomendasikan: unique pada `(source_system, reference_type, reference_value)` untuk referensi IDPEL yang aktif, jika aturan sistem sumber menjamin IDPEL unik. Satu customer dapat memiliki beberapa referensi eksternal dari sistem berbeda. Bila ditemukan IDPEL yang sudah terhubung ke customer lain, proses harus masuk antrean rekonsiliasi/merge terkontrol; jangan otomatis menggabungkan dua customer. Riwayat perubahan/penautan referensi wajib diaudit.

## 3. Tabel permohonan

### 3.1 `applications`

Kolom rancangan:

| Kolom | Tipe | Keterangan |
|---|---|---|
| id | UUID | PK |
| application_number | VARCHAR(50) | Nomor internal unik DISTRIVA |
| application_type | VARCHAR(5) | PB atau PD |
| transaction_type | VARCHAR(50) | Nilai asli/normalisasi jenis transaksi sumber |
| customer_id | UUID | FK customers |
| organizational_unit_id | UUID | FK organizational_units, wajib ULP |
| source_type | VARCHAR(30) | MANUAL / BOT_DAFTUNG |
| source_reference_id | VARCHAR(150) | ID unik sumber bila tersedia |
| source_created_at | TIMESTAMPTZ | Waktu dibuat sumber |
| imported_at | TIMESTAMPTZ | Waktu masuk DISTRIVA |
| service_address | TEXT | Alamat lokasi layanan |
| old_tariff_code | VARCHAR(30) | Tarif lama, nullable untuk PB |
| old_power_value | NUMERIC(14,3) | Nilai daya lama dari sumber |
| old_power_unit | VARCHAR(10) | Satuan sumber, mis. VA/kVA |
| new_tariff_code | VARCHAR(30) | Tarif baru |
| new_power_value | NUMERIC(14,3) | Nilai daya baru dari sumber |
| new_power_unit | VARCHAR(10) | Satuan sumber, mis. VA/kVA |
| delta_power_kva | NUMERIC(14,3) | Hasil normalisasi daya untuk kalkulasi |
| sar_package | VARCHAR(150) | Paket SAR sumber |
| total_cost | NUMERIC(18,2) | Total biaya yang ditetapkan/diimpor; bukan bukti pembayaran |
| service_criteria | VARCHAR(50) | Kriteria TMP sumber, mis. `05 Hari` |
| requires_drawing | BOOLEAN | Kondisional |
| requires_feasibility_study | BOOLEAN | Kondisional |
| requires_network_extension | BOOLEAN | Kondisional |
| current_status | VARCHAR(50) | Status internal DISTRIVA |
| submitted_at, completed_at | TIMESTAMPTZ | Waktu proses. `completed_at`: untuk **PB** berisi tanggal sambung = tanggal pertama status eksternal `PEREMAJAAN` di EIS (diisi saat impor EIS bila masih kosong, dan untuk data lama lewat `php artisan distriva:applications-backfill-connection-date`; tidak menimpa nilai dari penutupan WO internal); PD tidak diisi dari EIS karena tanggal `PEREMAJAAN`-nya adalah tanggal naik daya |
| created_by | UUID | FK users, nullable untuk proses sistem sesuai aturan |
| created_at, updated_at | TIMESTAMPTZ | Timestamp |

Aturan:
- `application_type` hanya `PB` atau `PD`; `transaction_type` menyimpan istilah sumber seperti `PASANG BARU` tanpa menjadikannya pengganti tipe internal.
- PB: daya lama untuk perhitungan dianggap nol. PD: daya delta = daya baru − daya lama.
- Nilai dan satuan daya sumber harus dipertahankan. Contoh spreadsheet `DAYA_BARU=900` perlu disimpan sebagai nilai sumber beserta satuannya yang dikonfirmasi; jangan menganggap otomatis 900 kVA. Normalisasi ke kVA hanya dilakukan setelah satuan terverifikasi.
- `organizational_unit_id` harus menunjuk unit bertipe ULP. UP3 didapat melalui relasi organisasi, bukan disimpan redundan kecuali ada kebutuhan snapshot yang jelas.
- Sumber eksternal tidak boleh mengubah data yang telah diproses tanpa aturan revisi dan audit.

## 4. Impor Bot Daftung

### 4.1 `application_import_batches`

Mencatat satu batch impor: `id UUID`, `source_system`, `batch_reference`, `started_at`, `completed_at`, `total_records`, `success_count`, `rejected_count`, `status`, `initiated_by`.

### 4.2 `application_import_staging`

Mencatat baris mentah sebelum menjadi permohonan resmi: `id UUID`, `batch_id`, `source_reference_id`, `payload JSONB`, `validation_status`, `validation_errors JSONB`, `application_id nullable`, `processed_at`, `created_at`.

`source_reference_id` unik dalam lingkup `source_system` jika sumber menyediakan ID stabil. Jika tidak tersedia, gunakan strategi idempotensi berbasis kombinasi referensi bisnis yang disetujui; jangan membuat dedup key spekulatif tanpa validasi.

Alur: import → staging → validasi → preview → pelengkapan nomor telepon → konfirmasi → `applications`. Record invalid masuk review; record yang sudah diproses tidak di-overwrite diam-diam.

### 4.3 Pemetaan kolom spreadsheet Bot Daftung

| Kolom sumber | Target DISTRIVA | Catatan |
|---|---|---|
| NOAGENDA | `application_external_references` (`AGENDA`) | String, melekat pada permohonan terkait; bukan identitas customer |
| NO_REGISTRASI | `application_external_references` (`PAYMENT_REGISTER`) | String, melekat pada permohonan terkait; bukan identitas customer |
| IDPEL | `customer_external_references` (`IDPEL`) | String; nullable untuk PB baru |
| NAMA | `customers.name` | Nama pelanggan |
| ALAMAT | `applications.service_address` | Alamat lokasi layanan |
| TARIF_LAMA | `applications.old_tariff_code` | Nullable untuk PB |
| DAYA_LAMA | `applications.old_power_value` + unit | Unit perlu dikonfirmasi dari kontrak data |
| TARIF_BARU | `applications.new_tariff_code` | Referensi master tarif |
| DAYA_BARU | `applications.new_power_value` + unit | Jangan infer unit dari angka saja |
| JENIS_TRANSAKSI | `applications.transaction_type` + mapping `application_type` | Contoh PASANG BARU → PB |
| PAKET_SAR | `applications.sar_package` | Nilai sumber |
| TOTALBIAYA | `applications.total_cost` | Bukan otomatis pembayaran terverifikasi |
| TGLBAYAR | `application_payments.paid_at` / staging payment evidence | Tanggal sumber; verifikasi tetap diperlukan |
| DURASI_HARI_KERJA | external status history `service_days` | Nilai sumber eksternal |
| KRITERIA_TMP | `applications.service_criteria` | Simpan teks asli, mis. `05 Hari` |
| STATUS_PERMOHONAN | external status history | Simpan sebagai status eksternal |
| TGL_UPDATE_PERMOHONAN | external status history `observed_at` | Timestamp update sumber |

Payload asli baris sumber harus tetap disimpan dalam staging atau arsip impor yang dapat ditelusuri. Jangan menganggap seluruh kolom spreadsheet sebagai status internal.

## 5. Referensi eksternal dan status

### 5.1 `application_external_references`

Kolom: `id UUID`, `application_id`, `external_system`, `reference_type` (`AGENDA`/`PAYMENT_REGISTER`), `reference_number VARCHAR`, `registration_source` (`API`/`MANUAL`/`BOT_DAFTUNG` sesuai asal), `received_at`, `received_by`, `external_created_at`, `is_active`, `raw_reference JSONB`.

Relasi utama: `customers 1:N applications`; `customers 1:N customer_external_references`; `applications 1:N application_external_references`. IDPEL berada pada customer, sedangkan No. Register dan No. Agenda melekat pada permohonan yang bersangkutan. Satu IDPEL dapat memiliki banyak No. Register dan No. Agenda melalui banyak permohonan. Nomor Register/Agenda dapat belum ada pada permohonan baru dan ditambahkan saat diterbitkan. Jika ada penerbitan ulang/koreksi, simpan riwayat referensi; jangan menimpa atau menghapus nomor sebelumnya. Nilai disimpan sebagai string untuk menjaga digit awal dan menghindari overflow.

### 5.2 `application_external_status_histories`

Kolom: `id UUID`, `application_id`, `external_reference_id`, `external_system`, `external_status_code`, `external_status_name`, `service_days`, `observed_at`, `received_at`, `source_payload JSONB`.

Status dari Bot Daftung/EIS AP2T tidak menggantikan `applications.current_status`.

### 5.3 `external_status_mappings`

Mapping opsional dan berversi/terkelola: `external_system`, `external_status_code`, `external_status_name`, `internal_status nullable`, `is_active`, effective dates. Status eksternal seperti `PEREMAJAAN` tetap disimpan asli; pemetaan ke status internal hanya jika aturan bisnis telah disetujui.

## 6. Pembayaran

### `application_payments`

Kolom: `id UUID`, `application_id`, `external_system`, `external_transaction_id`, `payment_reference`, `amount NUMERIC(18,2)`, `currency`, `payment_status`, `paid_at`, `verified_at`, `verification_source`, `verified_by`, `source_payload JSONB`, timestamps.

Status: `PENDING`, `PAID`, `FAILED`, `EXPIRED`, `REVERSED`, `REFUNDED`.

`TOTALBIAYA` pada spreadsheet dipetakan ke total biaya permohonan (`applications.total_cost`), bukan otomatis ke pembayaran yang diterima. `TGLBAYAR` adalah bukti/tanggal sumber yang harus diverifikasi melalui integrasi pembayaran atau prosedur verifikasi manual resmi. Workflow baru boleh beralih ke `REGISTRATION_PAID` setelah status pembayaran terverifikasi `PAID`. Callback harus idempotent; reversal/refund tidak dianggap pembayaran berhasil.

## 7. Survei

### `application_surveys`

Identitas satu pekerjaan/kunjungan survei: `id UUID`, `application_id`, `survey_number`, `current_status`, `assigned_to`, `scheduled_at`, `started_at`, `completed_at`, `created_by`, timestamps.

### `application_survey_versions`

Versi hasil survei: `id UUID`, `survey_id`, `version_number`, `survey_date`, `findings`, `technical_recommendation`, `requires_drawing`, `requires_network_extension`, `requires_feasibility_study`, `surveyor_id`, `submitted_at`, `reviewed_by`, `reviewed_at`, `status`.

### `application_survey_measurements`

Data terstruktur untuk koordinat, jarak jaringan, jenis jaringan, kapasitas trafo, kondisi jaringan, kebutuhan konstruksi, dan parameter teknis. Jenis/kolom pengukuran final mengikuti formulir survei resmi. Foto/dokumen tetap melalui modul dokumen.

**Catatan actor authorization v3.7.0:** kolom `assigned_to`, `surveyor_id`, dan `reviewed_by` adalah relasi actor pada rancangan schema, bukan penetapan role. Role pemberi tugas, surveyor, reviewer, kebutuhan approval formal, aturan surveyor-versus-reviewer, serta role pemeriksa administratif/teknis application belum diputuskan. Jangan memberi grant ke `TEKNIK` hanya berdasarkan nama role; lihat O-036/O-038 dan actor matrix di dokumen 34.

## 8. Task dan SLA

Gunakan tabel yang telah dirancang pada T3.3: `sla_configurations`, `application_tasks`, `application_task_assignments`, `application_task_reviews`, `application_revisions`, `sla_tracking_histories`, dan `application_notifications`. Jangan membuat mekanisme task kedua. Satu task memiliki satu assignee utama dan dapat memiliki beberapa kontributor. SLA internal dan SLA pelayanan PB/PD terpisah; snapshot kebijakan disimpan per transaksi. Aturan pause/resume menunggu keputusan kebijakan SLA.

## 9. Status workflow internal

`applications.current_status` menyimpan status terkini; seluruh perubahan disimpan pada `application_status_histories` (`id`, `application_id`, `from_status`, `to_status`, `changed_by`, `changed_at`, `reason`, `reference_type`, `reference_id`). Status internal mengikuti workflow T3.2: survey wajib; drawing/feasibility kondisional; menunggu register eksternal; pembayaran terverifikasi; cabang konstruksi hanya bila perluasan jaringan; meter installation diverifikasi sebelum `COMPLETED`.

Jangan menjadikan `PEREMAJAAN` atau status sumber lainnya sebagai enum internal tanpa keputusan mapping.

## 10. Constraint dan indeks awal

- Unique `application_number`.
- Unique `(source_type, source_reference_id)` ketika source reference tersedia, dengan partial unique index untuk nilai non-null.
- FK ULP harus divalidasi sebagai unit `ULP` melalui trigger/service constraint yang teruji.
- `application_type` CHECK `PB`,`PD`.
- Numeric untuk daya, biaya, pembayaran; tidak menggunakan floating point.
- Index `(organizational_unit_id, current_status, submitted_at)`.
- Index `(application_id, observed_at)` untuk histori eksternal.
- Unique nomor transaksi eksternal per provider jika provider menjamin keunikan.
- Unique `(survey_id, version_number)`.
- Index task berdasarkan aplikasi/status dan assignee/status.
- Nomor agenda/register disimpan VARCHAR, bukan numeric.
- Semua timestamp proses memakai `TIMESTAMPTZ`; tanggal sumber yang hanya berupa tanggal tetap disimpan sebagai DATE jika tidak memiliki waktu.

## 11. Keputusan dan isu terbuka

### Ditetapkan
1. Satu customer internal dapat memiliki banyak permohonan; satu IDPEL tetap menjadi identitas pelanggan PLN dan dapat terkait dengan banyak permohonan.
2. IDPEL disimpan sebagai referensi eksternal pada customer, bukan pada aplikasi dan bukan primary key.
3. No. Register (`PAYMENT_REGISTER`) dan No. Agenda (`AGENDA`) disimpan sebagai referensi eksternal per permohonan; keduanya tidak wajib tersedia pada saat permohonan dibuat.
4. Nomor telepon wajib tersedia sebelum permohonan resmi diajukan/diproses; data impor boleh masuk staging tanpa nomor telepon.
5. Petugas NIAGA_RETAIL melengkapi nomor telepon sebelum submit.
6. Nomor Agenda dan Nomor Registrasi merupakan referensi eksternal berbeda.
7. IDPEL adalah referensi eksternal, bukan primary key pelanggan.
8. `TOTALBIAYA` bukan otomatis pembayaran terverifikasi; `TGLBAYAR` perlu validasi.
9. `STATUS_PERMOHONAN` dan `DURASI_HARI_KERJA` merupakan data status/layanan eksternal.
10. Payload sumber dipertahankan untuk audit dan rekonsiliasi.

### Masih terbuka
1. Pilihan strategi identitas pelanggan: fleksibel dengan customer master atau model lain; pengguna belum mengonfirmasi opsi final.
2. Kontrak API Bot Daftung dan metode sinkronisasi Google Spreadsheet/API.
3. Definisi satuan `DAYA_LAMA` dan `DAYA_BARU` pada feed aktual; contoh `900` tidak cukup untuk menyimpulkan satuan.
4. Apakah NOAGENDA dan NO_REGISTRASI selalu diterbitkan pada waktu yang sama serta aturan koreksinya.
5. Provider/endpoint dan kontrak pembayaran serta otoritas verifikasi manual.
6. Kamus kode status eksternal dan definisi `KRITERIA_TMP`.
7. Formulir survei resmi dan daftar measurement final.
8. Aturan pause/resume SLA.

Desain konseptual T4.2.3 diperbarui setelah contoh spreadsheet, kebijakan nomor telepon, serta kardinalitas customer–IDPEL–permohonan–register/agenda dikonfirmasi. Belum ada migration, seeder, API integration, atau workflow code yang dibuat.


## 13. Sinkronisasi status Bot Daftung berdasarkan No. Agenda (keputusan v3.0)

### 13.1 Ruang lingkup pembaruan record yang sudah ada

Untuk record permohonan yang sudah tersimpan di DISTRIVA dan memiliki No. Agenda yang cocok dengan data Bot Daftung, sinkronisasi rutin hanya boleh memperbarui tiga atribut berikut:

| Kolom sumber Bot Daftung | Atribut terkini pada DISTRIVA | Perlakuan |
|---|---|---|
| `DURASI_HARI_KERJA` | `service_days` / durasi layanan eksternal terkini | Boleh diperbarui |
| `STATUS_PERMOHONAN` | `external_status` / status eksternal terkini | Boleh diperbarui |
| `TGL_UPDATE_PERMOHONAN` | `source_updated_at` / waktu update sumber terkini | Boleh diperbarui |

Tidak ada kolom lain yang boleh diubah oleh jalur sinkronisasi status ini. Secara khusus, sinkronisasi tidak boleh mengubah nama, nomor telepon, alamat layanan, tarif, daya, paket SAR, total biaya, tanggal pembayaran, IDPEL, No. Register, data survei, gambar teknik, BOM, RAB, KKF, status workflow internal, penugasan, atau data approval.

### 13.2 Kunci pencocokan

- `NOAGENDA` digunakan untuk mencari `application_external_references` dengan `reference_type = AGENDA`.
- Pencocokan dilakukan pada nomor agenda yang dinormalisasi secara aman (trim spasi luar; jangan menghilangkan nol awal atau mengubahnya menjadi angka).
- No. Agenda harus mengidentifikasi tepat satu permohonan. Jika tidak ditemukan, record tidak masuk jalur update status existing. Jika ditemukan lebih dari satu, record masuk antrean rekonsiliasi dan tidak ada update otomatis.
- `IDPEL` bukan kunci update status permohonan; satu IDPEL dapat memiliki banyak permohonan.

### 13.3 Aturan penerapan update

1. Validasi keberadaan `NOAGENDA` dan kecocokan tepat satu application.
2. Baca nilai tiga kolom yang diizinkan.
3. Bandingkan `TGL_UPDATE_PERMOHONAN` sumber dengan `source_updated_at` terakhir yang telah diterapkan.
4. Jika timestamp sumber lebih lama, abaikan sebagai data stale dan catat hasil sinkronisasi. Jika sama tetapi payload status berbeda, tandai konflik untuk pemeriksaan; jangan menebak urutan. Jika lebih baru, terapkan hanya tiga atribut yang diizinkan.
5. Jika timestamp sumber sama dan nilai tiga atribut sama, perlakukan sebagai no-op/idempotent; tidak perlu membuat histori perubahan duplikat.
6. Simpan snapshot histori sebelum/sesudah, sumber, waktu diterima (`synced_at`), dan batch/log referensinya.
7. `TGL_UPDATE_PERMOHONAN` adalah waktu perubahan menurut sumber, sedangkan `synced_at` adalah waktu DISTRIVA menerima/menerapkan data; keduanya tidak boleh dicampur.

Jika tanggal sumber tidak valid/kosong, atau formatnya ambigu, record dikarantina untuk pemeriksaan; jangan mengganti timestamp yang valid dengan nilai kosong. Zona waktu dan format tanggal final harus ditetapkan dalam kontrak feed.

### 13.4 Data baru dan record tanpa agenda

Aturan tiga kolom di atas khusus untuk update permohonan existing yang cocok melalui No. Agenda. Data baru atau record yang belum memiliki No. Agenda tetap melalui staging dan validasi impor awal. Data tersebut tidak boleh dipaksakan masuk ke jalur update status berdasarkan IDPEL, nama, atau alamat. Strategi identitas sumber untuk permohonan baru masih menunggu konfirmasi ketersediaan ID unik Bot Daftung atau aturan deduplikasi alternatif.

### 13.5 Penyimpanan latest state dan histori

`application_external_status_histories` menyimpan setiap snapshot status eksternal yang berhasil diterapkan, minimal: `id`, `application_id`, `agenda_reference_id` atau `agenda_number`, `service_days`, `external_status`, `source_updated_at`, `synced_at`, `source_system`, `import_batch_id`, `payload_hash`, `change_kind`, serta metadata audit. Indeks pencarian diperlukan pada `application_id`, `agenda_number`, dan `source_updated_at`.

Atribut latest state dapat disimpan sebagai proyeksi pada tabel status eksternal terkini atau dihitung dari histori terakhir yang valid. Apabila disimpan sebagai kolom/cache pada `applications`, hanya tiga atribut eksternal tersebut yang boleh ditulis oleh service sinkronisasi dan harus jelas terpisah dari `current_status` workflow internal.

### 13.6 Batas kewenangan sinkronisasi

Service Bot Daftung status-sync harus menggunakan allowlist tiga field, bukan mass assignment seluruh payload. Pembaruan dilakukan dalam transaksi database, dicatat dalam `external_sync_logs`, dan tidak memanggil perubahan workflow internal. Perubahan pada kolom di luar allowlist harus ditolak/diabaikan dan dicatat sebagai anomali integrasi.

## 14. Keputusan dan isu terbuka (pembaruan v3.1)

### Ditetapkan
- Untuk permohonan existing yang cocok tepat melalui No. Agenda, Bot Daftung hanya boleh memperbarui `DURASI_HARI_KERJA`, `STATUS_PERMOHONAN`, dan `TGL_UPDATE_PERMOHONAN`.
- Seluruh data lain pada customer dan application tidak boleh ditimpa oleh jalur sinkronisasi status.
- Update status eksternal tidak boleh mengubah workflow internal DISTRIVA.
- Timestamp sumber yang lebih lama tidak boleh menimpa snapshot lebih baru; konflik timestamp sama dengan isi berbeda perlu review.
- Histori status dan waktu sinkronisasi harus dipertahankan.

### Masih terbuka
- Ketersediaan ID unik sumber untuk permohonan baru yang belum memiliki No. Agenda.
- Format/t zona waktu resmi `TGL_UPDATE_PERMOHONAN` dan kontrak feed/API.
- Kamus nilai `STATUS_PERMOHONAN` dan validasi rentang `DURASI_HARI_KERJA`.
- Mekanisme transport Bot Daftung (API atau file) dan autentikasinya.

## 15. Aturan final rentang unduhan Bot Daftung (v3.1)

Bot Daftung mengunduh data berdasarkan tanggal permohonan pertama kali dibuat. File memuat data lama dan baru di rentang pilihan; batch dapat overlap. `period_start`/`period_end` menjelaskan cakupan tanggal pembuatan, sedangkan `TGL_UPDATE_PERMOHONAN` menjadi acuan kebaruan status. Record yang tidak muncul pada batch berikutnya tidak berarti dihapus/selesai. Lihat `25-T4.2.3-BOT-DAFTUNG-SYNC-RULES.md`.
