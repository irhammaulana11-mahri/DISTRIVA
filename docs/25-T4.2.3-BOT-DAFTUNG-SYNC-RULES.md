# T4.2.3 — Aturan Final Impor dan Sinkronisasi Bot Daftung

Versi dokumentasi: 3.1  
Tanggal: 5 November 2026  
Status: keputusan bisnis sinkronisasi rentang tanggal dikonfirmasi; implementasi belum dilakukan.

## 1. Karakteristik feed Bot Daftung

Bot Daftung mengunduh data dari aplikasi internal berdasarkan **tanggal permohonan pertama kali dibuat**. File hasil unduhan memuat data lama dan data baru yang termasuk dalam rentang tanggal yang dipilih. Karena rentang dapat berubah dan saling tumpang tindih, file bukan full snapshot seluruh database dan bukan incremental murni.

Metadata batch wajib menyimpan `period_start`, `period_end`, `downloaded_at`, `imported_at`, `source_system`, `file_name`, dan checksum file bila transport berupa file. Rentang tersebut adalah kriteria pemilihan data sumber, bukan tanggal perubahan status.

## 2. Dua jalur pemrosesan

### 2.1 Permohonan existing dengan No. Agenda

1. Cari No. Agenda yang cocok secara tepat dan unik.
2. Jika ditemukan tepat satu application, jalankan status-sync.
3. Hanya `DURASI_HARI_KERJA`, `STATUS_PERMOHONAN`, dan `TGL_UPDATE_PERMOHONAN` yang boleh diperbarui.
4. Field customer/application lain tidak boleh ditimpa.
5. Status eksternal tidak boleh mengubah workflow internal DISTRIVA.
6. Simpan histori perubahan dan metadata batch.
7. Jika nilai tidak berubah, jangan membuat histori perubahan status duplikat.

Jika No. Agenda tidak ditemukan atau menghasilkan lebih dari satu kandidat, jangan update otomatis; masukkan ke antrean rekonsiliasi.

### 2.2 Data baru atau belum memiliki No. Agenda

1. Simpan payload asli pada staging.
2. Jika No. Agenda atau No. Register tersedia, gunakan sebagai kandidat pencocokan sesuai jenis referensi.
3. Jika keduanya belum tersedia, lakukan pemeriksaan kandidat duplikasi berdasarkan kombinasi atribut permohonan.
4. Nama, telepon, alamat, jenis transaksi, tarif/daya, dan tanggal hanya indikator kandidat, bukan identitas permanen.
5. Jika kandidat ditemukan, tahan untuk pemeriksaan petugas; jangan auto-merge.
6. Jika tidak ditemukan kandidat, data dapat diteruskan sebagai permohonan baru setelah validasi.
7. `application_id` DISTRIVA menjadi identitas internal. Bot Daftung tidak menyediakan source ID unik permanen.

## 3. Batasan deduplikasi

- `payload_hash` hanya fingerprint payload, bukan primary key permohonan.
- Baris identik di batch berbeda dapat ditandai sebagai kemungkinan pengiriman ulang, tetapi perlu referensi tepercaya atau pemeriksaan.
- Tidak munculnya permohonan pada batch berikutnya **tidak** berarti permohonan dihapus, dibatalkan, atau selesai.
- Batch dengan rentang tanggal tumpang tindih adalah kondisi normal.
- No. Agenda harus unik dalam cakupan sistem penerbit yang ditetapkan; konflik tidak boleh diselesaikan dengan memilih record arbitrer.
- No. Register hanya menjadi pencocokan alternatif jika jenis referensi, penerbit, dan keunikannya terverifikasi.

## 4. Urutan prioritas dan timestamp

Untuk status-sync, `TGL_UPDATE_PERMOHONAN` adalah acuan kebaruan perubahan dari sumber. `downloaded_at` dan `imported_at` hanya metadata pengambilan/penerimaan.

- Timestamp sumber lebih lama daripada status terakhir yang diterapkan: jangan timpa.
- Timestamp sumber sama dan nilai sama: perlakukan sebagai pengulangan tanpa perubahan.
- Timestamp sumber sama tetapi nilai berbeda: masukkan rekonsiliasi.
- Format tanggal, timezone, dan presisi timestamp harus dikonfirmasi sebelum implementasi.

## 5. Tabel dan atribut

`application_import_batches`: `period_start`, `period_end`, `downloaded_at`, `imported_at`, `source_system`, `file_name`, checksum, jumlah baris, dan status batch.

`application_import_staging`: `batch_id`, `source_row_number`, `raw_payload`, `normalized_payload`, `payload_hash`, hasil validasi, status deduplikasi, dan `matched_application_id`.

`application_external_status_histories`: `application_id`, No. Agenda, tiga nilai status eksternal, `source_updated_at`, `synced_at`, batch sumber, dan payload/fingerprint audit.

`application_external_references` menyimpan No. Agenda dan No. Register per application. `customer_external_references` menyimpan IDPEL per customer.

## 6. Invarian keamanan data

Status-sync memakai allowlist eksplisit tiga field, bukan mass assignment payload. Pembaruan dilakukan dalam transaksi database dan dicatat dengan batch, waktu, nilai sebelum/sesudah, dan keputusan sinkronisasi. Jalur ini tidak boleh mengubah nama, telepon, alamat, tarif, daya, total biaya, pembayaran, IDPEL, No. Register, survei, gambar, BOM, RAB, KKF, maupun workflow internal.

## 7. Isu teknis yang masih perlu konfirmasi

- Apakah batas awal dan akhir rentang tanggal bersifat inklusif.
- Format tanggal dan timezone `TGL_UPDATE_PERMOHONAN`.
- Kamus status dan validasi `DURASI_HARI_KERJA`.
- Penerbit dan cakupan keunikan No. Agenda/No. Register.
- Kanal pertukaran, autentikasi, jadwal, dan kontrak API/file.
- Contoh file dari beberapa rentang untuk uji overlap dan deduplikasi.
