# Activation and recovery with OTP (owner decision 2026-11-06)
## Decision implemented
Administrators still add users on the web, but they no longer issue passwords. New accounts are PENDING_ACTIVATION; the person activates with a one-time code sent by e-mail and/or WhatsApp and sets their own password. Locked/forgotten accounts are recovered the same way. (Supersedes the 24 h temporary password of docs/16; recorded in docs/18 and docs/15.)

## Defects found while building (all fixed)
1. **Shared rate-limit counter (pre-existing).** Unnamed `throttle:N,M` middleware keys requests by domain|IP only, so login, password change and OTP shared one counter per IP: activation followed by login within a minute got 429, and users behind one office IP would lock each other out. Replaced by named limiters (`login` per address+IP 10/min, `otp-request`, `otp-verify` per address+IP, `password-change` per user, `admin` per user). Regression tests added.
2. Login limiter (5/min) collided with the 5-failure account lockout (6th attempt answered 429 instead of the lockout message) and delayed the "unlock at once" promise: limiter raised to 10/min per address and cleared on successful activation/recovery.
3. Test-tool issues, not application defects: my WhatsApp sink only parsed form bodies while the owner's .env uses JSON (fixed to accept both); an E2E assertion expected the first failed attempt to show "terkunci".
